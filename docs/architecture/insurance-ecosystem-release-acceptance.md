## Release criteria

Do not mark a participant workflow accepted until the named participant representative completes the scenario and records evidence. All critical/high authorization defects must be resolved and retested. Finance acceptance must reconcile sample source transactions to posted balances. Legal and regulatory acceptance must be recorded by qualified stakeholders for the actual deployment jurisdiction and data flows.

Production release additionally requires:

1. A reviewed production backup and successful restore rehearsal.
2. A reviewed migration plan and data mapping for every legacy insurer-partner row, including any legacy-wide scopes.
3. Staging migration and rollback rehearsal on a production-like data copy.
4. Pilot agreement from each participating organization, user support contacts, and a scheduled rollback owner.
5. A post-deployment smoke test for login/company switching, quote, policy, payment, claim, partner restriction, and TIRAMIS callbacks.

## Phase 11–13 verification checklist

Use the same release record for each target environment. Automated checks demonstrate code behavior; they do not replace finance or participant approval.

### Phase 11 — finance evidence

- Recalculate an agreed commission example from the frozen distribution/pricing snapshot and compare gross, rate, amount, currency, and intermediary attribution.
- Exercise accrual approval/reversal, commission payment allocation, payment reversal, receipt allocation/reversal, and idempotent retries. Confirm every correction creates a linked reversal/journal and preserves the original record.
- Import a bank/provider statement with exact, ambiguous, duplicate, unmatched, reversed, wrong-currency, wrong-amount, and fee/charge rows. Verify duplicate rows are excluded from totals, disputed/ambiguous rows remain reviewable, and one payment/receipt cannot be posted twice.
- Compare statement opening + movement total to closing balance; investigate any difference before approval.
- Reconcile intermediary settlement totals by insurer, intermediary, branch, and sales point, then reconcile reinsurance premium accounts, settlement, and recovery receipts to counterpart statements.
- Record calculation fixture IDs, statement hashes/references, currency/rounding policy, ledger account mapping, expected and actual totals, finance reviewer, result, and approval date. Never attach bank credentials or full account numbers.

### Phase 12 — participant evidence

For each row in the participant matrix, record environment, organization ID, test-account ID, workflow, expected result, actual result, evidence reference, defect ID, tester, participant approver, and timestamps. Use separate accounts for each organization. Include allowed and denied cases for product, action, branch, customer, policy, claim, document, commission, treaty, and placement scope. Verify error messages do not reveal another organization's record existence.

### Phase 13 — security and operations evidence

- Run cross-company negative tests for API reads/writes, background jobs, report exports/downloads, uploaded files, portal attachments, payment callbacks, TIRAMIS callbacks/retries, and integration credentials.
- Record the exact release SHA, environment, migration list, security test version, findings by severity, remediation commit, and retest evidence. Penetration testing and privacy/legal approval must be issued by the responsible qualified reviewer.
- Perform a backup restore into an isolated target. Record backup reference, restore timestamp, recovery point/time measurements, row-count or checksum validation, owner, and evidence reference. Do not place backup data in source control.
- Rotate each integration credential using the environment's secret manager. Verify the new key, verify rejection of the revoked key after the approved overlap window, and record only key version/rotation dates.
- Send a controlled alert for API readiness failure, queue/Redis failure, storage failure, TIRAMIS callback backlog, and finance outbox backlog. Record alert route, delivery time, acknowledgement, and closure.
- Review production deployment context: environment, database host identity (no secrets), TLS, proxy hops, CORS allowlist, private document root/bucket, malware scanner mode, queue/cache mode, metrics authorization, audit hash chain, migration policy, and release evidence gates.

The environment's release-gate flags must remain false until evidence is attached and an authorized owner approves them. A local passing build cannot set backup/restore, security, UAT, business, or technical approval flags.

## Known limitations to resolve or explicitly accept

- The local development migration state does not establish production schema or data readiness.
- TIRAMIS service keys must carry endpoint capabilities and source IP restrictions. The application now enforces HTTP and RPC scopes and has focused denial tests; still rotate or update legacy keys with empty capabilities and verify source IP restrictions in each target environment before release.
- Reinsurance broker and reinsurer business relationships must be active on both relevant sides for a broker-arranged facultative offer; configure and verify those appointments before live placement.
- The configured legacy `LEGACY` partner scope deliberately retains prior access behavior until each relationship is reviewed and converted; it must not be treated as least-privilege approval.
- Agreement amendment documents currently use the existing agreement document URL field. Confirm that deployment storage, retention, access control, and evidence integrity meet the organization's policy before production use.
- Business acceptance, legal/regulatory review, and production approval require authorized human representatives and are not inferred from automated tests.
