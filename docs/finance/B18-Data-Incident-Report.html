Controlled recovery plan — not executed

Restoring development would replace current data, including possible post-reset changes. Recovery needs a separate explicit approval after the target, backup, reconciliation and write pause are reviewed. No restore approval is inferred from the investigation or Git push request.

  1. Review and explicitly approve recovery of insurance_portal_db from the verified 17 November 21:47:50 pre-reset backup. This replaces the current public schema and can replace post-reset changes; this investigation does not authorise that action.
  2. Before execution, stop business writes and pause background writers in all chats and services that target this database. Recheck identity, database name and source port, capture a new private full backup of the current state, record its hash and verify it on another isolated copy.
  3. Recheck the candidate backup hash against this report. Rehearse the exact restore and application startup using a disposable clone and the current finance branch. Match all four protected invoice header/item hashes, the 376-table inventory, the 93-entry migration ledger, original company/user permissions, legal entity/book and ten draft setup rows. Keep B18 unapplied and every accounting policy inactive.
  4. Produce a reconciliation of any post-reset additions or changes against the verified pre-reset copy. Preserve that current-state backup; do not silently discard or merge newer financial records. Resolve collisions before cutover.
  5. Only after the approved recovery gate, restore the verified pre-reset backup to development during the controlled write pause. Do not run the reset/seeder workflow, reapply already-present migrations or apply B18 as part of recovery.
  6. Verify paid invoice and item hashes again, permissions and independent Finance access, draft setup state, ledger/schema, balances and quotation/payment/claims read views. Resume writers only after reconciliation. Retain the current-state backup for rollback and record the approval, commands and verification results.

Future prevention — recommendations only

  • Reject development schema resets containing Finance records unless the operator explicitly approves the affected database and protected accounting populations.
  • Use separate databases per concurrent development/rehearsal task and record the target identity in maintenance evidence.
  • Use an application database role without schema-drop authority; row immutability alone cannot protect against an owner-level schema drop.
  • Require restore-tested private backups and a maintenance audit for destructive resets; file existence and nonzero size alone are limited backup checks.

The reset script's existing backup check verifies a successful dump and a nonempty file. This investigation additionally performed a full isolated restore and data-hash reconciliation. No maintenance-script or application-code changes were made.
